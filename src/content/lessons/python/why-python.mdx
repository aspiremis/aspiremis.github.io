You have a working MATLAB track and a campus licence. Learning a second language needs
a reason better than "everyone uses it."

Here is the reason, and also the honest limits of it.

## Different origins, different defaults

MATLAB was built in 1979 so that engineering students could do matrix algebra without
writing Fortran. Everything about it follows from that — matrices are the fundamental
type, `*` means matrix multiplication, indexing starts at 1.

Python was built in 1989 as a **general-purpose language optimised for readability**.
Guido van Rossum's stated priority was code that is easy to read, because code is read
far more often than it is written.

<Analogy>
  MATLAB is a **specialist instrument** — a very good oscilloscope. Superb at the thing
  it was built for, awkward for anything else.

  Python is a **workshop**. Nothing in it is as specialised as the oscilloscope, but you
  can build almost anything, and someone has probably already built a tool for whatever
  you need.
</Analogy>

The most important consequence: **in Python, arrays are a library, not the language.**

```python
a = [1, 2, 3]
b = [4, 5, 6]
a * 2         # [1, 2, 3, 1, 2, 3]  — repeats the list!
a + b         # [1, 2, 3, 4, 5, 6]  — concatenates!
```

That is not "wrong". A Python `list` is a general-purpose container of anything, and
those are the sensible operations on a container. Numerical arrays come from **NumPy**,
and there `a * 2` does what you expect.

This trips up every MATLAB user exactly once, and it explains the structure of the whole
scientific stack.

## The stack

| MATLAB | Python | What it does |
|---|---|---|
| core arrays | **NumPy** | n-dimensional arrays, broadcasting, linear algebra |
| tables | **pandas** | labelled tabular data, time series |
| plotting | **Matplotlib** | figures (plus seaborn, plotly for other styles) |
| toolboxes | **SciPy** | optimisation, sparse, signal processing, statistics |
| Statistics & ML | **scikit-learn** | the standard ML library |
| Simulink | *no equivalent* | this is a real gap |
| Simscape Electrical | OpenDSS, **pandapower** | different tools, different strengths |

Each is a separate package you install and import. That feels fragmented at first and is
the source of the ecosystem's strength — anyone can write a package, so there is one for
almost everything.

<Callout type="engineering">
  The licence argument is the one that matters most for your career.

  Your IIT Bhubaneswar licence is excellent and it belongs to the institute. It will not
  follow you to a job that hasn't bought one, to a collaborator at another university, or
  to a reviewer who wants to check your results.

  A hosting-capacity study written in Python can be run by anyone who reads your paper.
  The same study in MATLAB can be run by people with a licence. For research that is
  supposed to be reproducible, that is a real difference — and it is why OpenDSS,
  pandapower and most published power-system tooling are Python-first.
</Callout>

## What Python is genuinely worse at

Being fair about this saves you from using it badly.

**Loops are slow — worse than MATLAB's.** A Python `for` loop over a million elements is
dramatically slower than the NumPy equivalent, and slower than the same loop in MATLAB.
The fix is the same as in MATLAB: vectorise. The penalty for not doing so is larger.

**No Simulink.** If your work involves block-diagram modelling of converters or machines,
MATLAB is simply the tool. There is no honest substitute.

**Environment management is a real chore.** MATLAB has one installation; Python has
virtual environments, package versions and occasional dependency conflicts. The next
lesson deals with it, and it is genuinely more setup than MATLAB asks of you.

**Indexing from 0**, and slices that exclude the endpoint. Both are defensible, both take
a fortnight to stop causing off-by-one errors.

## Learn both, in this order

You did MATLAB first because your coursework assumes it *now*. Python second, because:

- The second language is far easier. Most of what you learned — vectorisation, floating
  point, conditioning, validating against known results — is **ideas, not syntax**, and
  ideas transfer.
- The final module of this track is a direct MATLAB-to-Python translation guide, which
  only makes sense once both are familiar.

<Callout type="tip" title="Don't try to write MATLAB in Python">
  The most common failure mode for an experienced MATLAB user is writing Python that
  works and reads like a translation — index loops, no comprehensions, everything a
  2-D array.

  It runs. It is also slower and harder to read than idiomatic Python, and it means you
  spent the effort of learning a language without getting the benefit. This track flags
  the idiomatic form whenever there is one.
</Callout>

## Mini tasks

<Exercise n={1} kind="read" title="Which language?">
  Pick a language for each, and say why.

  1. Simulating a PWM inverter with a current controller
  2. Cleaning three years of half-hourly meter data with gaps and duplicates
  3. Running 500 OpenDSS scenarios and summarising the results
  4. A one-off matrix calculation for an assignment
  5. Code you want to publish alongside a paper

  <Solution>
    1. **MATLAB.** Simulink. No contest.
    2. **Python.** pandas handles missing data, duplicated timestamps and timezone
       arithmetic far more gracefully than MATLAB tables.
    3. **Python.** OpenDSS has a well-supported Python interface, and this is scripting
       and data handling rather than matrix mathematics.
    4. **Either — whichever is already open.** For a one-off, the tool you're fluent in
       wins.
    5. **Python**, if the choice is free. A reviewer without a MATLAB licence cannot run
       your code, and reproducibility is the point of publishing it.

    Notice that (4) has no principled answer. Not every choice is a considered one, and
    pretending otherwise wastes time.
  </Solution>
</Exercise>

<Exercise n={2} kind="predict" title="What does this do?">
  Predict the output, given that these are Python **lists**, not NumPy arrays.

  ```python
  v = [1, 2, 3]
  print(v * 2)
  print(v + [4])
  print(v * v)
  ```

  <Solution>
    - `v * 2` → `[1, 2, 3, 1, 2, 3]`. Multiplying a list by an integer **repeats** it.
    - `v + [4]` → `[1, 2, 3, 4]`. Plus **concatenates**.
    - `v * v` → **TypeError**. You cannot multiply a list by a list.

    None of this is arithmetic, because a list is a general container — it might hold
    strings, or other lists, or nothing at all. Repetition and concatenation are the
    operations that make sense for containers.

    Import NumPy and the picture changes completely:

    ```python
    import numpy as np
    v = np.array([1, 2, 3])
    v * 2      # array([2, 4, 6])   — element-wise, as you'd expect
    v * v      # array([1, 4, 9])   — element-wise, no dot needed
    ```

    That last line is worth noting now: NumPy's `*` is **element-wise by default**, the
    opposite of MATLAB. Matrix multiplication is `@`. The next module covers it properly.
  </Solution>
</Exercise>

<KeyIdea>
  MATLAB is a **specialist instrument**; Python is a **workshop**. The key structural
  consequence is that arrays are a *library* in Python, not the language — which is why
  `[1,2,3] * 2` repeats, and why NumPy exists.
</KeyIdea>
